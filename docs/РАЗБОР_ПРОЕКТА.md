# Разбор проекта ASIC ToolBox EXE

## Область разбора

Разобрана текущая ветка `main` репозитория `k3rNexAI/ASIC_ToolBox_EXE`. Исходники не изменялись. Рассмотрены исходные серверные, браузерные, алгоритмические, тестовые и сборочные скрипты, их связанные страницы и данные. `node_modules` — сторонние зависимости, они не являются кодом приложения и отдельно построчно не разбирались. Файлы `ASIC ToolBox.exe`, `runtime/node.exe`, `tools/grpcurl.exe`, `public/app-icon.ico` — двоичные артефакты/ресурсы, не читаемый исходный код; их поведение объясняется по соответствующим скриптам, которые их запускают или встраивают.

> Формат диапазонов: номера строк относятся к состоянию файлов в репозитории на момент анализа; при изменении файлов номера сдвинутся.

## Схема программы и основной поток вызовов

1. `npm start` выполняет `node server.js` (`package.json:6–11`). Сервер загружает настройки/данные, поднимает локальный HTTP-сервер.
2. Браузер запрашивает HTML, CSS и JS из `public/`. Главная страница `index.html` подключает `app.js`, `scanner-settings.js`, `theme.js`; страница массового сканирования `maps.html` подключает `scanner-settings.js`, `maps.js`, `theme.js`.
3. UI вызывает `/api/...` через локальный HTTP API. Главный серверный обработчик находится в `server.js:1302–1875`.
4. При сканировании `scanIps()` запускает конкурентные проверки адресов через `scanOne()`. В зависимости от выбранного протокола вызываются `restScanOne()`, `gRPCScanOne()` или `scanOneLegacy()`. Последняя нормализует старый API через `miner-compat.js`.
5. По полученным устройствам сервер формирует сводки и `mixes()` из `mix-algorithm.js`. UI рисует результаты и при включённом наблюдении периодически вызывает `/api/monitor`.
6. Данные ЦОДов хранятся в `state.json`, карты — в `maps.json`, планы — в `saves/`. Это локальные JSON-данные, а не логика программы.

### `server.js` — HTTP API, сканирование, сохранение и управление ASIC (1926 строк)

**Инициализация, пути и миграция (1–74).** ESM-импорты включают Node HTTP/fs/path/child_process, SSH, `miner-compat.js` и `mix-algorithm.js` (1–16). Константы определяют каталог приложения/данных, порты и параметры сканирования (18–35). `embeddedAsset(name)` (36–38) читает файл, встроенный в SEA, либо возвращает null; `resolveGrpcurl()` (40–56) выбирает grpcurl из SEA-ресурса или файла `tools/grpcurl.exe`. `migratePortableData()` (58–74) переносит известные файлы из старой portable-папки в новый data-dir, но только если назначения ещё нет.

**Настройки и HTTP-агенты (75–196).** `boundedInt` ограничивает число min/max; `envInt` применяет это к переменным окружения. `normalizeScannerSettings` формирует объект настроек со значениями по умолчанию и валидируемыми протоколом, портами, timeout, batch/max IP, keep-alive и учётными данными (101–132). `createRestAgent` настраивает keep-alive HTTP; `retireRestAgent` закрывает устаревший агент после завершения его запросов (134–150). `loadScannerSettings` читает локальный JSON, нормализует/мигрирует параметры и поднимает соответствующий агент (152–178). `publicScannerSettings` предназначен для ответа UI (179–195); фактически spread всего объекта следует перепроверить перед публикацией: в коде может попасть пароль, хотя README обещает обратное.

**Отмена, состояние и JSON-хранилище (197–358).** `scanAbortError` создаёт стандартную ошибку отмены; `throwIfScanAborted` немедленно прерывает операцию при abort signal. `unwrapState` достаёт список из массива или известных контейнеров старого формата (204–218); `parseStateText` пытается JSON и legacy-вариант (219–240); `readStateFile` оборачивает чтение/ошибки (241–255). `codRecords` выбирает основной или legacy источник, `readCods` дополнительно нормализует и сортирует ЦОДы (256–272). `readMaps` загружает объект карт с пустым fallback; `writeJsonAtomic` сохраняет через временный файл и rename, при необходимости оставляет `.bak`; `writeMaps`/`writeCods` — специализированные обёртки, `defaultMap` — шаблон карты (273–313). `safeSegment`, `localDate`, `saveRoot`, `savePath` формируют безопасные пути сохранений; `savePath` не даёт выйти за корень `saves`. `readSavedList` ищет манифесты и строит отсортированный список (314–358).

**Управление платами и NoPIC (359–487).** `enableAllBoards(recipients)` для каждого ASIC получает gRPC-токен/список плат и включает их; на устройство возвращается отдельный результат/ошибка. `readNoPicExperimentalMode(ip, signal)` через SSH читает настройку, ограничивает время и умеет отменяться. `attachNoPicMode` присоединяет её к результату сканирования. `setNoPicExperimental(ip, enabled)` меняет настройку через SSH/временный конфиг на устройстве. Поток вызова: результат сканирования или `/api/boards/configure` → соответствующая функция; эти операции реально меняют состояние ASIC.

**Общие HTTP/IP помощники (488–579).** `json(res, code, data)` сериализует JSON-ответ; `body(req)` собирает и парсит тело запроса; `validName` проверяет имя; `ipToNum`/`numToIp` конвертируют IPv4; `expandRange(start,end,cidr)` проверяет CIDR/границы и разворачивает список IP, ограничивая общий размер. `parseMinerApiJson` извлекает JSON из ответа старого API. `apiCall(ip, command, timeoutMs, signal)` создаёт TCP-запрос старому miner API и завершает сокет на ответе/ошибке/timeout/отмене. `asArray`, `cleanModel` — нормализаторы структур/модели.

**Протоколы сканирования (580–1089).** `grpcCall` (581–597) запускает grpcurl, передаёт сервис, JSON-сообщение, токен, timeout/abort и разбирает результат. `restCall` (598–672) делает HTTP-запрос через переиспользуемый агент, управляет таймаутом и отменой, проверяет код ответа и размер/JSON. `restScanOne` (673–787) логинится к REST, запрашивает данные ASIC/плат, диагностические ошибки/охлаждение; собирает общую запись устройства со статусом, платами, чипами и хешрейтом. Ошибки необязательных диагностических запросов не всегда отменяют основной результат. `firstArray`, `chipCount`, `boardHashrateGh`, `boardIsWorking` (788–810) приводят разные схемы полей к общему формату. `gRPCScanOne` (811–894) получает аналогичный снимок по gRPC и нормализует его.

`scanOneLegacy` (895–941) делает несколько TCP-команд (VERSION/SUMMARY/DEVS/DEVDETAILS/STATS), превращает данные посредством `normalizeCgminerResult`, возвращает унифицированное устройство. `offlineDevice` (942–955) — стандартная запись для недоступного IP. `scanOne(ip, protocol, signal)` (956–993) выбирает порядок через `scanProtocolOrder`, пробует протоколы, возвращает первый успешный результат; обычные ошибки идут в offline-модель, отмена пробрасывается. При необходимости дополняет запись NoPIC по SSH. `scanSummary` (994–1010) считает агрегаты. `scanIps` (1011–1088) удаляет дубли/невалидные IP, ограничивает количество, запускает пул worker-ов до заданного concurrency, репортит прогресс и при hybrid/legacy может выполнить REST-уточнение плат. `scanCod` (1089–1090) получает IP из записи ЦОДа и передаёт в `scanIps`.

**Демо и статические ресурсы (1091–1245).** `demoResults(cod)` возвращает заранее заданные образцы статусов/плат; используется только для `demo:true`, это не настоящее сканирование. `serveFile(req,res)` (1219–1245) обслуживает файлы из `public` либо SEA assets и выставляет базовые типы контента. Запросы не `/api` направляются сюда.

**Резервная копия (1246–1301).** `readBackupTree(dir,relative)` рекурсивно читает JSON в дереве сохранений с фильтрацией временных/backup файлов. `buildBackup()` собирает конфигурацию ЦОДов, карты, legacy-state и сохранённые JSON в экспорт; это экспорт, а не импорт/восстановление.

**HTTP-маршруты и когда вызываются (1302–1875).** `http.createServer` маршрутизирует запросы по URL/методу; API ветки вызываются браузером. `GET/POST /api/scanner-settings` отдаёт/сохраняет настройки. `/api/scan-all/progress` и `/api/scan/cancel` читают/меняют прогресс и общий AbortController. `/api/health`, `/api/backup/export` — состояние и экспорт. `/api/cods`, `/api/state-diagnostics` — список и диагностика; далее POST/PATCH/reorder/DELETE выполняют CRUD ЦОДов с проверкой полей и записью state. `/api/maps` и `/api/maps/:id` читают/записывают карту (размеры, IP, позиции ячеек). `POST /api/scan-all` сериализует массовый скан: проверяет выбранные ЦОДы, запускает скан по ним, сохраняет прогресс, вычисляет миксы; `finally` снимает блокировку даже при ошибке/отмене. `/api/saves` создаёт и читает snapshot-файлы. `/api/boards/configure` вызывает enable/disable и изменение NoPIC, `/api/boards/enable` включает все платы, `/api/miner/resume` посылает resume. `/api/monitor` обновляет выбранные устройства без полного скана. `POST /api/scan` сканирует один ЦОД и возвращает устройства, сводку, миксы. Неизвестный API возвращает ошибку, общий `catch` формирует JSON 500.

`listenOnAvailablePort()` (1876–1914) пробует порт `PORT` и последующие, слушает `HOST`, выводит локальный адрес; для SEA при соответствующей конфигурации открывает браузер. Внизу (1915–1926) стартовая цепочка выполняет перенос данных → загрузку настроек → listen, а при завершении уничтожает HTTP-агенты.

**Практические замечания к серверу.** У штатной проверки нет тестов всех HTTP-маршрутов и сетевых ошибок. Наблюдаются потенциально важные места для будущей разработки: пароль в публичных настройках следует исключить; ограничить максимальное тело `body()`; валидировать размеры карты и IP при записи; подумать об очереди для конкурентных read-modify-write; разбор старого JS state привести к действительно поддерживаемому формату. Приведённые пункты — наблюдения по реализации, не изменения.

### `miner-compat.js` — совместимость legacy API и нормализация

- `numeric(value)` (2–9) приводит число/строку к конечному числу. `scanProtocolOrder(protocol)` (12–17) задаёт последовательность попыток: `auto` — REST→gRPC→legacy, `hybrid` фактически legacy, иначе один режим. `needsRestBoardDetails(device)` (19–26) определяет, когда после legacy/hybrid нужен уточняющий REST по платам.
- `rateFields` задаёт известные имена полей и единицы. `cgminerHashrateGh(row)` (47–90) распознаёт хешрейт прямыми полями или по нормализованному имени; переводит H/KH/MH/TH в GH/s, нераспознанное значение возвращает null.
- `firstArray`, `idOf`, `statusOf`, `isBadStatus`, `isHashDevice`, `chipCountOf`, `modelOf` (93–113) — небольшие адаптеры вариантов ответа miner API: массивы, ID, статус, тип устройства, число чипов и модель.
- `normalizeCgminerResult(input)` (116–245) принимает IP/порт и блоки VERSION/SUMMARY/DEVS/DEVDETAILS/STATS; выбирает строки плат, сопоставляет детали по ID/индексу, нормализует speed/status/chips, определяет работающие платы, версию/семейство прошивки, модель, общий хешрейт, ошибки и `ratio`. Это вызывается legacy-сканированием из `server.js:895–941`; интерфейс получает тот же формат независимо от API.
- `flattenState(value, output)` (248–258) рекурсивно извлекает значения/ключи; `braiinsMinerState(value)` (261–292) ищет слова состояния в вложенных данных и определяет сон/остановку/запуск/работу/неизвестное. Вызывается нормализатором legacy-ответов.

Ключевая семантика: строка без распознанной единицы в некоторых путях трактуется как GH/s; одно только summary неизвестной прошивки не гарантирует наличие реальных плат. Десятичная запятая удаляется как разделитель тысяч, поэтому числа локального формата с запятой требуют осторожности.

### `mix-algorithm.js` — баланс плат

`selectDonors(items, needed)` (9–20) решает subset-sum: карта `states` хранит первый набор доноров для каждой достижимой суммы; обход снимка состояний назад предотвращает повторное использование донора. Нет точной суммы — пустой результат. Экспортируемая `mixes(devices)` (29–95) оставляет онлайн-устройства с 1 или 2 работающими платами, разбивает по `boardModel || model`, сортирует получателей по дефициту (2/3 перед 1/3), перебирает префиксы-кандидаты и ищет точную сумму донорских плат. Доноры передают все платы и помечаются `0/3`; входные объекты копируются. Выход содержит группы, выбранных/неиспользованных доноров/получателей и счётчики. Модель жёстко рассчитана на 3 платы и совместимость определяется строковым ключом модели.

### Лаунчеры

`launcher.js` — ESM-лаунчер portable режима. `request(port, pathname)` проверяет HTTP/health с timeout; `openBrowser(url)` запускает системный браузер Windows; `stopServer()` завершает дочерний процесс один раз; `main()` проверяет наличие `runtime/node.exe` и `server.js`, ищет уже работающий экземпляр, выбирает порт, запускает Node и ждёт готовности, затем открывает UI. Включены обработчики завершения процесса. Это отдельный вариант и не является главным npm `start` или используемой SEA-сборкой.

`launcher.cjs` — CommonJS-вариант того же сценария. `request()` проверяет HTTP, `isPortFree()` проверяет TCP-порт, `openBrowser()` вызывает Windows shell, `stopServer()` останавливает дочерний процесс, `main()` проверяет существующий сервер, находит порт, запускает runtime и ждёт HTTP readiness. Ожидает `runtime/node.exe` и `server.js` рядом с исполняемой структурой. `package.json check` проверяет синтаксис именно CJS-версии, но не выполняет её на Linux.

`run-windows.cmd` — короткая Windows-команда запуска portable-папки: задаёт рабочий каталог, проверяет наличие runtime/server, устанавливает базовую конфигурацию окружения и запускает сервер через `runtime\node.exe`. Не собирает EXE и не содержит самостоятельной логики сканирования.

### `scripts/build-sea.mjs` — упаковка в один Windows EXE

Импорты Node fs/path/crypto/child_process и `esbuild` (1–7); константы корня, `.sea-build`, `dist`, output и SEA fuse (9–13). `run(command,args)` запускает дочерний инструмент в корне, выводит его логи и прекращает сборку при ошибке/timeout (15–23). Проверяется Windows и Node 22+ (25–30). Удаляются предыдущие `WORK`/`OUTPUT`, создаются каталоги (32–35). `esbuild` бандлит `server.js` в минифицированный CommonJS bundle под node22; `cpu-features`/нативные `.node` исключаются (37–50). Список ресурсов формируется из корневых файлов `public`, `package.json` и `tools/grpcurl.exe`; обязательные ресурсы проверяются на существование (52–67). Создаётся SEA config и Node строит payload blob (69–82). Копируется текущий `process.execPath` в имя EXE; загружается закреплённый по URL `rcedit`, проверяется его SHA256, ставится `public/app-icon.ico` (83–96). Через `postject` payload инжектируется в исполняемый файл с SEA fuse (97–105). Итоговый путь выводится (107–110). Примечание: сборка удаляет папку `dist` и `.sea-build`, но не меняет корневой готовый EXE.

### `.github/workflows/build-windows-exe.yml`

Workflow запускается вручную либо при push в `main`, если изменён один из перечисленных файлов сборки/сервера/интерфейса/зависимостей (1–16). На `windows-latest` checkout, Node 22 и `npm ci`; далее `npm run check` и сборка (17–28). PowerShell smoke test стартует готовый EXE с фиксированным тестовым портом и без открытия браузера, до 25 секунд ищет HTML с `ASIC ToolBox`, проверяет ранний выход/таймаут и всегда завершает процесс (29–64). При успехе EXE публикуется GitHub artifact (65–70). Smoke test подтверждает старт и отдачу главной страницы, но не функциональность ASIC-сети.

## Браузерные скрипты `public/`

### `public/app.js` — одиночный ЦОД, миксы и мониторинг (968 строк)

Загружается `index.html`. Глобальное состояние скрипта включает ЦОДы, выбранный ЦОД, устройства, миксы, сводку, доноров/реципиентов и таймер сканирования. `$`, `toast`, `api`, `rangeLabel` (1–27) — DOM, уведомления, fetch+JSON+HTTP error и форматирование диапазона.

`groupedCods()`/`renderCods()` (29–118) собирают группы ЦОДов, выводят меню/карточки и после динамического `innerHTML` привязывают click-обработчики выбора/редактирования/удаления. `openCodDialog()` заполняет форму; `moveCod()` вызывает серверный reorder; `selectCod()` обновляет выбранный объект и повторный рендер (119–160). `escapeHtml`, `statusChip`, `formatGh`, `boardRows` (161–206) защищают/форматируют ячейки результатов. `localScanSummary`, `renderScanSummary`, `renderResults` (207–265) считают fallback-статистику и выводят результат с учётом фильтров.

`roleDevice`, `labelPayload`, `printLabelEntries`, `printLabels`, `printGroup` (266–306) готовят данные и окно печати. `renderMixes()` (307–343) выводит группы и связывает кнопки печати. Форма ЦОДа (344–376) превращает значения в POST/PATCH к API. `selectedProtocol`, `protocolLabel`, `updateProtocolControls` (377–407) синхронизируют UI-протокол; событие `scanner-settings-applied` меняет состояние кнопки (408–413). ### `public/maps.js` — флот, массовый scan и мониторинг карт (816 строк)

Собственное состояние: `cods`, `fleetResults`, кеш карт, множества закреплённых и восстановившихся IP. `$`, `api`, `isProblemDevice`, `esc`, `toast`, `suffix`, `resultDevice`, `deviceState`, `cap`, `mapCells`, `temperatureText` (1–89) — обёртки запросов, классификация неисправностей, экранирование, форматирование и геометрия карты. `ipSortValue`, `readDefects`, `formatGh`, `formatCompactHashrate` (90–120) поддерживают сортировку/локальную регистрацию дефектов и значения хешрейта.

`renderRedDevices()` (121–170) строит подробные карточки неисправных устройств и действия по платам/NoPIC/Resume/сохранению. `mapHtml()` (171–210) сопоставляет ячейки карты с результатами; `renderFleetMaps()` (211–305) сохраняет состояние раскрытия и пользовательского ввода между перерисовками и повторно привязывает динамические действия. `renderChecks()`/`chosen()` (306–331) рисуют выбор ЦОДов; `renderGlobalRecoveredList()` (332–346) выводит закреплённые восстановленные устройства. `summary()` (347–418) агрегирует статусы, время и latency. `loadMaps()` (419–436) загружает карты параллельно.

`scan(isDemo)` (438–503) проверяет выбор, блокирует кнопки, ждёт настройки, вызывает `/api/scan-all`, обновляет результаты/карты/сводку, запускает периодический мониторинг, а `finally` восстанавливает UI. `renderSidebarCods()` (504–528) рисует навигацию. `drawScanProgress`, `startScanProgress`, `stopScanProgress` (529–578) опрашивают `/api/scan-all/progress` с защитой от старых ответов и показывают процент. `drawMonitoredResults`, `renderDefectRegistry`, `refreshDefectRegistry`, `bindDefectRegistryActions`, `printDefectStickers` (579–626) синхронизируют мониторинг и список дефектов из localStorage. `bindDeviceActions()` (627–745) связывает изменение плат, NoPIC, дефектов, Resume, pin/unpin и печати с API/локальным состоянием. `pollMaps()` (746–788) каждые 5 секунд запрашивает `/api/monitor` только по закреплённым проблемным устройствам, обновляет состояние и перерисовывает. `init()` (790–816) загружает ЦОДы, создаёт выбор и назначает кнопки запуска/отмены/demo.

### `public/map-builder.js` — редактор карты (199 строк)

`$`, `api`, `esc`, `toast` (1–23) — общие DOM/API-помощники. `ipN`/`ipT` (25–34) переводят IPv4; `ips(c,n)` перечисляет start–end, пропуская последние октеты .0/.255; `cap` считает вместимость; `suffix` форматирует адрес. `cod`, `cells`, `meta` (61–78) находят выбранный ЦОД, сохраняют прежние ячейки и создают новые IP, подготавливают подпись карты. `render()` (79–121) формирует HTML сетки «стеллаж/полка/ASIC» и через prompt редактирует IP. `load(id)` загружает карту API; `generate()` очищает ячейки, чтобы пересчитать; `save()` отправляет геометрию и ячейки через PUT (122–167). `renderSidebarCods()` показывает группы, `init()` загружает список и связывает действия; вызов `init().catch(...)` происходит сразу (168–199). Важный нюанс: генератор `ips()` использует start/end и сам CIDR не разворачивает; для ЦОДа только с CIDR автозаполнение может быть пустым.

### `public/scanner-settings.js` — форма настроек сканера (210 строк)

Самовызывающаяся функция проверяет наличие `#scannerSettingsMount`; если его нет — завершает работу. `mount.innerHTML` строит форму с протоколом, batch/max IP, портами, таймаутами, keep-alive и учётными данными (1–59). `setValue`, `syncProtocolControls` заполняют UI, обновляют флажки REST/gRPC/legacy и рассылку `scanner-settings-applied`; `fill()` сохраняет настройки в `window.appliedScanSettings`, заполняет поля и вызывает синхронизацию (61–126). Далее обработчики input/change/password меняют статус и видимость пароля (127–150). Submit (151–186) формирует типизированный payload, POST `/api/scanner-settings`, обновляет форму по ответу и возвращает кнопку в нормальное состояние. Начальный GET выполняется сразу; `window.scannerSettingsReady` становится Promise, который используют `app.js` и `maps.js` перед запуском скана. `fetchJson()` централизует разбор JSON/HTTP ошибок (188–210).

### `public/guide.js` — боковой список и навигация руководства (68 строк)

`safe()` экранирует строки. IIFE немедленно делает GET `/api/cods`, строит боковые группы ЦОДов и при ошибке выводит сообщение (1–43). Затем связывает ссылки оглавления с якорями и, если доступен браузерный `IntersectionObserver`, отмечает активный раздел по пересечению (46–68). Сканирование и изменение оборудования этим файлом не выполняется.

### `public/theme.js` — темы (57 строк)

Хранит допустимые темы и `storageKey`; `normalize()` отбрасывает неизвестные значения. `apply(value,persist)` задаёт `data-theme` на корневом элементе, синхронизирует переключатели и при необходимости пишет localStorage. При старте восстанавливает выбор, обрабатывает событие change, а `storage` отражает выбор из другой вкладки (1–57). Подключается внизу страниц UI.

## HTML/CSS и другие файлы проекта

`public/index.html`, `maps.html`, `map-builder.html`, `guide.html` — шаблоны разделов приложения; они задают DOM-элементы, ID и порядок подключения JS. `public/styles.css`, `themes.css` — оформление и варианты цветов. `public/manus-routes.json` — декларативная конфигурация маршрутов/публикации, не функция приложения. `maps.json`, `state.json`, `saves/**` — состояние и примеры сохранений. `CHANGELOG.md`, `README.md`, `WINDOWS.md`, `WINDOWS_EXE.md`, `docs/**`, `ideas.md` — документация/план, а не исполняемые скрипты. `.gitignore`, `.prettierignore`, `.prettierrc.json` — правила git/форматирования.

`docs/JAVASCRIPT_GUIDE.md` — отдельная учебная документация по JS проекта; её полезно читать параллельно с исходниками. Остальные docs раскрывают API, модель данных, конфигурацию, алгоритм, эксплуатацию, Braiins API и историю.

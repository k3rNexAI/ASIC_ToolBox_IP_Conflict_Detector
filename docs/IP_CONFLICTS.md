# Поиск нескольких ASIC на одном IP

В ASIC ToolBox добавлен отдельный раздел **«Конфликты IP»** (`/ip-conflicts.html`). Он запускается по требованию и использует сохранённую карту выбранного ЦОДа, если в ней есть валидные IP; иначе опрашивает диапазон/CIDR ЦОДа. Один IP проверяется повторно заданное число раундов (2–6, по умолчанию 3). Между раундами немедленной паузы нет: это повторные последовательные сетевые запросы, ограниченные обычной параллельностью сканера.

В меню доступны текущие протоколы сканера: Braiins REST, gRPC, legacy TCP 4028, Auto и Hybrid. Сетевые запросы выполняет локальный сервер приложения. Используются те же сохранённые настройки пользователя/пароля, таймаутов, портов и параллельности, что и в основном сканере. Проверка занимает больше времени и создаёт больше запросов, чем обычный скан: количество попыток равно числу IP, умноженному на число раундов.

## Что сравнивается

1. **Серийный номер ASIC**, если используемый REST/gRPC-ответ его публикует. Разные серийные номера с одного IP — наиболее сильное доступное приложению подтверждение смены ASIC за адресом. Не всякая прошивка или версия API раскрывает серийный номер.
2. **MAC из таблицы соседей компьютера**, полученный командами `ip neigh`/`arp` на Linux/macOS либо `arp -a` на Windows. Разные MAC без серийного номера отмечаются как конфликт, но это надёжный сигнал только когда компьютер находится в том же L2/VLAN-сегменте. Через маршрутизатор таблица может содержать MAC gateway; запись может быть закэширована и показывать лишь одно из устройств.
3. **Аппаратный отпечаток** из модели ASIC, версии и модели плат. Его различие отмечается как «требует проверки», а не как доказательство: прошивка/конфигурация/платы могут меняться, а часть полей может быть неполной.

Офлайн-ответы не считаются отдельной идентичностью. Результат показывает найденные сигналы по каждому IP, число завершённых попыток и число успешных ответов.

## Ограничения и безопасная интерпретация

- Одинаковый IP сам по себе не означает, что за ним два устройства: возможны NAT, прокси, балансировщик, DHCP-переприсвоение, кеши и нестабильная сеть.
- Эта проверка **не** очищает ARP/neighbor cache, не меняет настройки устройств, DHCP или сетевого оборудования и не выполняет сканирование subnet за пределами выбранного ЦОДа.
- Отсутствие обнаруженного конфликта не доказывает, что конфликтов нет. Два устройства могут поочерёдно отдавать одинаковый/неполный набор полей; API может не возвращать серийник; ARP может быть скрыт шлюзом.
- Для подтверждения сверьте DHCP lease, таблицу MAC-адресов и портов управляемого коммутатора, VLAN и физическое подключение. Это обычно сильнее одного MAC, увиденного с рабочего компьютера.
- На время проверки лучше находиться в сети управления ASIC и не запускать одновременно другое сканирование/мониторинг: штатная блокировка сервера предотвращает такие параллельные опросы.

## HTTP API

`POST /api/ip-conflicts`

```json
{
  "codId": "uuid-сохранённого-ЦОДа",
  "rounds": 3,
  "protocol": "rest"
}
```

`rounds` обязателен и должен быть целым числом от 2 до 6. `protocol` необязателен; применяются значения scanner settings. Успешный ответ содержит `scanSummary`, итоговый список `results`, обезличиваемые технические `observations` (IP, round, онлайн/оффлайн, serial/model/version/boardModel и MAC), и `cancelled`. Пароль ASIC в ответ не включается. Прогресс доступен через `GET /api/scan-all/progress`; отмена — существующим `POST /api/scan/cancel`.

Запуск возвращает HTTP 409, если уже выполняется скан или мониторинг; 404 — если ЦОД не найден; 400 — при неверном количестве раундов или превышении лимита адресов.

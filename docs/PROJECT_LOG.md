# Журнал проекта и план развития

## 2026-10-30 — IP conflict detector

- Добавлен самостоятельный раздел `/ip-conflicts.html` и API `POST /api/ip-conflicts`. Используются существующая карта/диапазон ЦОДа, Braiins REST/gRPC/legacy scanner pipeline, общий прогресс и общая отмена сканирования.
- Классификация различает несколько серийных номеров (сильный сигнал), MAC из локальной таблицы соседей без серийного номера (сильный лишь в локальном L2 сегменте) и несовпадение модели/версии/плат (только повод для проверки).
- Добавлены unit-тесты алгоритма, инструкция пользователя/API и навигация по разделу.
- Автоматические тесты и статический анализ выполняются командой `npm run check`. Реальные ASIC не опрашивались в среде разработки; на рабочей VLAN необходимо отдельно проверить какие serial-поля публикует установленная Braiins OS и как ведут себя ARP/neigh записи.
- Ограничение: без уникального serial (или доступной локальной ARP-таблицы) повторные идентичные ответы не позволяют достоверно отличить два ASIC, поочерёдно отвечающих с одним IP. Для окончательной проверки используйте DHCP и FDB/MAC-таблицу коммутатора.

Последнее обновление: 2026-10-19  
Текущая версия: 1.5.0  
Целевая среда: Windows 11, доменный ПК, запуск от обычного пользователя, один компьютер без отдельного сервера.

## Принципы проекта

1. Сохранять штатно работающие функции из исходного `ASIC_ToolBox_speed_v3.zip`, включая REST-сканирование и включение hashboard.
2. Не менять рабочие контракты Braiins API без теста на реальном устройстве или проверенном ответе.
3. Все новые изменения документировать в `CHANGELOG.md` и этом журнале.
4. Перед изменениями формата данных предусматривать обратную совместимость и резервную копию.
5. По умолчанию сервер слушает только `127.0.0.1`; не открывать его в сеть без отдельной модели аутентификации.
6. Для эксплуатационных команд фиксировать запрос, ответ и результат проверки; не объявлять операцию успешной только на основании отправки команды.

## 1.1.0 — устойчивость локальных данных и экспорт резервной копии

### Реализовано

- Добавлен `GET /api/health`, который возвращает доступность приложения, время проверки и флаги активного сканирования/мониторинга.
- Добавлен `GET /api/backup/export`, выгружающий JSON с `state.json`, `maps.json`, legacy `state.js` и JSON-файлами в `saves/`; ссылка на скачивание добавлена в верхнюю панель интерфейса.
- `state.json` и `maps.json` записываются через временный файл с последующим переименованием.
- Перед записью состояния и карт создаются локальные `.bak`-копии предыдущих файлов.
- Добавлен журнал изменений и список следующей работы.

### Проверено в среде разработки

- `node --check server.js`
- `node --check public/app.js`
- `node --check public/maps.js`

### Не проверено в этой итерации

- Выполнение REST/gRPC-команд на реальном парке ASIC.
- Восстановление из экспортированной резервной копии на отдельной копии каталога.
- Поведение записи при аварийном отключении питания на целевом Windows-ПК.

## Текущие архитектурные ограничения

- Данные хранятся в JSON и каталоге `saves/`, а не в транзакционной базе.
- История полных сканов не сохраняется автоматически как отдельные неизменяемые записи.
- Мониторинг выполняется по запросу, а не как долговременная фоновая служба.
- Расчёт совместимости опирается на `boardModel`; формальная версионируемая матрица совместимости ещё не реализована.
- Встроенная пользовательская авторизация отсутствует. Это приемлемо только для loopback-доступа с доверенного ПК.
- Экспорт — JSON-файл, а не ZIP. Он включает сохранённые планы, но не содержит бинарники, `node.exe`, `grpcurl` или секреты окружения.

## План следующих итераций

### P1 — история сканов и аудит операций

- Каждому скану присваивать ID и сохранять дату, ЦОД, протокол, параметры, итоговые счётчики и устройства.
- Не перезаписывать результаты предыдущих сканов.
- Вести журнал выполнения микса: исходный план, подтверждение физического переноса, команды включения, повторный опрос и итоговая сверка.
- Добавить просмотр различий между двумя сканами.

### P2 — совместимость плат и Mix Engine

- Ввести файл/экран матрицы совместимости с версией, источником и статусом подтверждения каждой комбинации.
- Разделить модель ASIC, модель платы и совместимость платы.
- Проверять инварианты плана: доноры после операции `0/3`, реципиенты `3/3`, ни одна плата не назначена дважды, количество плат совпадает.
- Сохранять объяснение, почему устройство включено или исключено из плана.
- Не менять действующий алгоритм по умолчанию до сравнения результатов на реальных сохранённых наборах.

### P3 — эксплуатационная диагностика

- Статистика по ЦОДам, моделям и статусам плат.
- Сравнение хешрейта и ошибок между сканами.
- Экспорт CSV для инвентаризации и отчётов.
- Настраиваемый лимит параллельности с предупреждением при чрезмерных значениях.

### P4 — тестирование и упаковка

- Тесты парсинга ответов REST/gRPC/legacy на обезличенных fixture-файлах.
- Регрессионные тесты алгоритма микса на сохранённых наборах.
- Smoke-тест портативного запуска в профиле обычного пользователя Windows.
- Проверка резервного экспорта/восстановления на копии данных.

## Правило приёмки

Изменение считается завершённым, когда обновлены код и документация, выполнены доступные автоматические проверки, перечислены непроверенные условия и подготовлены инструкции отката. Реальные операции управления ASIC отдельно проверяются в тестовом окне или на выбранном тестовом устройстве.

## 2026-10-24 — v1.1.1: scan timing and navigation

### Fixed

- The map-results table previously tried to display `durationMs`, while the server emits `scanDurationMs`; the row mapping also omitted duration and protocol. It now displays the correct full scan duration and protocol.

### Added

- Each IP scan now records `responseTimeMs` in milliseconds, measured around the full selected scan/fallback attempt. `scanDurationMs` remains present on each device for compatibility.
- The datacenter summary shows minimum, maximum and arithmetic mean latency among devices that successfully responded. Offline devices are not included in the latency statistics, but remain represented in the offline count.
- The main ASIC result table displays per-device response time. Map-cell tooltips include it too.
- All three pages now share the same navigation entries and grouped datacenter list.

### Validation and limitations

- Static syntax checks passed for the server and all relevant client scripts.
- Actual REST/gRPC/TCP timing against production ASICs was not performed during this patch. Latency reflects total time spent in the selected protocol flow, including fallback attempts when `auto` is selected; it is not a pure network RTT measurement.

## 2026-10-24 — версия 1.1.2

- Исправлено различие областей сканирования: `/api/scan` теперь использует список IP из `maps.json`, если он настроен и содержит адреса. В противном случае сохраняется совместимость со сканированием диапазона.
- Дедупликация IP из карты предотвращает повторные запросы к одному устройству.
- Статистика отклика в сводной таблице карты отображается компактными блоками MIN / СР. / MAX.
- Проверки: синтаксис Node.js и клиентских скриптов; далее требуется проверка на реальном ЦОДе.

## 2026-10-24 — v1.1.3: корректная классификация и итоговая статистика

- В сводке страницы карт OFFLINE классифицируется раньше состояния плат. Устройство с `online === false` или `status === 'offline'` учитывается только в колонке «Офлайн», даже если у него `ratio === '0/3'` или `status === 'check'`.
- Красные устройства считаются только среди ответивших устройств; зелёные, жёлтые, красные и офлайн теперь не должны пересекаться для штатных статусов сканера.
- В статистике отклика используется единый источник `responseTimeMs` с fallback на `scanDurationMs` для совместимости со старыми результатами. Офлайн/неответившие устройства не включаются в MIN/СР./MAX.
- В итоговую строку добавлены суммарная длительность сканирования выбранных ЦОДов и MIN/СР./MAX по всем успешным ответам. Поскольку сервер обрабатывает выбранные ЦОДы последовательно, суммарная длительность рассчитана как сумма `scanDurationMs` каждого ЦОДа.
- Проверены синтаксис серверного кода и клиентских скриптов. Реальные ASIC не опрашивались; фактические значения проверяются при следующем сканировании в рабочей сети.
